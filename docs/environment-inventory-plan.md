# KaliMac 下一阶段计划：环境资源查看与显式清理

> 版本：v1，2026-10-01（Asia/Shanghai）。状态：**待实施**。
> 本轮只编写计划，不创建功能分支、不开发、不测试、不操作容器、不提交或推送。
> 建议实施分支：`codex/environment-inventory`（尚未创建）。
> 规划基线：`c9f297b`，当前 `codex/environment-switch` 已包含环境切换、安装版验收与真实强杀实验。
> 前序设计：[环境事务 ADR](adr-environment-transactions.md)；结果：[环境切换进度](environment-switch-progress.md)。

## 1. 目标与优先级

环境切换和回退会保留旧容器。当前 retained 账本只增不删，下一阶段解决：

1. **看清资源**：哪些是当前环境、回退目标、普通保留环境、事务资源或异常资源？
2. **明确删除**：用户能删除一个确认不需要的、已停止的保留容器。
3. **结果可信**：删除与账本更新中断后可以核实并收尾，不误报成功、不误删其他资源。

实施顺序：先交付只读 `km env list`，再交付定向 `km env remove <完整ID>`。
两个增量独立验收；清理未完成不得妨碍 list 的独立交付，但总体目标不据此缩减。

## 2. 本轮范围

### 2.1 新能力

```bash
km env list
km env remove <完整容器ID> --dry-run
km env remove <完整容器ID>
km env remove <完整容器ID> --yes
```

- list 只看当前项目和固定本地引擎，不是全局 Docker 容器浏览器。
- remove 一次只接受一个完整 ID，不接受名称、短 ID、多个目标或通配符。
- 正常删除只允许当前项目 retained 账本内、归属匹配且状态为 `exited` 的容器。
- 已被外部删除的 retained 条目可经明确不存在核验后收尾，但必须说明“仅清理失效记录”。
- 延用 `km env recover` 承担已确认删除操作的中断收尾；不得套用“重新创建旧容器”的恢复语义。

### 2.2 不做

- 不做批量 prune、自动定时清理、按磁盘阈值清理或全局管理。
- 不接受 `--force`，不自动 stop/unpause/kill，不终止运行中的 retained 容器。
- 不删除 CURRENT、PREVIOUS、未完成事务引用资源或未知归属资源。
- 不删除镜像、volume、bind mount 源目录，不执行 `docker system/container/image prune`。
- 不新增 JSON、任意多代回退、镜像构建/安装或 GUI。
- 不承诺删除后的环境恢复；容器可写层删除是不可逆操作。
- 不自动提交、推送、合并、打 tag 或发布。

## 3. list 行为合同

### 3.1 展示结构

建议字段：`ROLE / GENERATION / CONTAINER_ID / NAME / STATE / IMAGE_ID / REASON / REMOVABLE`。

| ROLE | 来源与含义 | 删除资格 |
| --- | --- | --- |
| CURRENT | state.json 当前身份 | 永久保护 |
| PREVIOUS | previous.json 回退目标 | 永久保护 |
| RETAINED | retained.json 有意保留容器 | 重新预检后判定 |
| TRANSACTION | 未完成事务引用的资源 | 保护，先 recover |
| UNTRACKED | 同项目标签但不在已知记录集合中 | 仅报告，不接管、不删除 |

- 输出完整容器 ID；名称只用于展示，不能作为删除键。
- 镜像、状态等来自已核验事实；缺失数据标“未核实”，不根据名称猜测。
- `MISSING` 表示在已确认引擎上明确不存在；`UNKNOWN` 表示查询失败；`CONFLICT` 表示身份不符。
- 将容器实际状态与记录角色分开：RETAINED 不代表一定已停止。
- 同一 ID 出现在多个互斥角色中属于记录冲突，默认保护，不按某个角色优先放行。
- 当前代代号可能因 rollback 返回旧值；列表不要把代号当作全局唯一、永远递增的资源标识。
- stable 排序：CURRENT、PREVIOUS、RETAINED、事务/异常信息；同类按可靠时间和完整 ID 排序。
- 本轮不展示不可靠的“预计释放磁盘空间”；镜像共享层与容器可写层不能混算。

### 3.2 查询完整性与只读性

- 不取会写文件的项目锁，不升级 schema、不补写记录、不引导脚本、不清扫会话。
- 使用固定 endpoint，列表枚举采用完整 ID，再对相关资源逐个核验；不将显示用短 ID用于删除匹配。
- 并发 switch/rollback/remove 可能改变记录：采取有界重读或一致性检查，变化持续时返回 UNKNOWN。
- 未完成事务可展示，但输出明确“需恢复”；不能把中间态当作健康资源总览。
- Docker 不可达时可展示本地记录，但明确为未核实，不宣称无容器或可删除。
- v1 项目仅显示当前容器；缺少 env 记录不触发迁移，也不虚构上一代或 retained。
- 账本中的明确缺失条目继续显示 MISSING，不因查看列表而删除。

## 4. remove 行为合同

### 4.1 预览与确认

- `--dry-run` 不写锁文件、状态、清理记录或日志，不执行 Docker 变更命令。
- 预览说明目标完整 ID、记录角色、实际状态、镜像、保留原因，以及保护检查结果。
- 预览必须提醒：**容器可写层内文件将永久丢失；不会删除共享项目文件，也不会删除镜像。**
- 交互执行要求明确确认；非交互必须显式 `--yes`；用户拒绝时零变更。
- `--yes` 仅代替确认，不绕过任何身份、角色、运行状态或事务门禁。
- 预览不是未来删除的授权快照；确认后取得锁并重新读取记录、查询目标。
- 若目标、角色或预览依赖记录发生变化，放弃本次操作并要求重新预览，不沿用过期确认。

### 4.2 删除资格判定

删除前必须同时满足：

1. 当前项目配置、state、previous、retained 可解析且 schema 支持。
2. endpoint 与项目记录一致；远程引擎、引擎漂移明确拒绝。
3. ID 为当前项目 retained 的精确完整 ID，且没有与 CURRENT/PREVIOUS/事务保护集合重叠。
4. 目标容器的完整 ID、名称、项目标签、镜像内容、挂载及已有代际/op 信息符合记录。
5. 如记录类型为历史 `probe-cleanup-failed`，必须识别探测容器的只读挂载规则；无法按其角色完整核验时拒绝，不能放宽为仅标签匹配。
6. 容器实际状态为 exited；running/paused/restarting/created/dead 等在第一版均明确拒绝。
7. 无其他未完成事务或删除操作；项目锁仍有效，保护集合已在锁内重读。

目标为“未知 ID”时，即使它不存在也不能清理任意记录或宣称删除成功。
同名新容器不能替代原 ID；原 ID缺失时不得删除该同名容器。

### 4.3 Docker 删除方式

- 使用普通 `docker rm <完整ID>`，**不带 `-f` 或 `-v`**。
- 不复用内部固定带 `-f` 的测试/失败清理 helper；实现前核实 runtime 接口行为。
- 外部进程在最终检查后重新启动容器时，普通 rm 应失败；不得自动升级为强制删除。
- Docker 返回 0 仍需确认目标 ID 已不存在，才进入成功收尾。
- rm 返回错误或响应丢失时重新核实实际状态；明确不存在可收尾，仍存在/未知不得报成功。

## 5. 输出与退出码

| 命令/场景 | 结果 | exit |
| --- | --- | --- |
| list 完整核实，含明确 MISSING 条目 | 展示事实；MISSING 附失效记录提示 | 0 |
| list 查询不完整、记录冲突/损坏、存在待恢复操作 | 展示可确认部分与错误；不宣称健康 | 1 |
| remove 预检通过、成功删除并收尾 | 明确预览通过或删除完成 | 0 |
| retained ID 已明确不存在，确认后移除失效记录 | 明确“仅清理记录”，不说刚删除了容器 | 0 |
| 不在 retained、目标受保护、状态不允许、身份冲突 | 非零，给出拒绝原因 | 1 |
| 无效/短 ID、未知选项、多个 ID、非交互缺确认 | 用法错误；无变更 | 2 |
| 用户拒绝 | `KM_CANCELED`，未执行 | 1 |
| 查询超时/引擎故障/操作未确认 | 既有 KM_* 错误，明确待核实阶段 | 1 |

优先复用 `KM_CONTAINER_CONFLICT`、`KM_RESOURCE_UNKNOWN`、`KM_TRANSACTION_PENDING`、
`KM_STATE_INVALID`、`KM_TIMEOUT` 等；若新增保护目标错误码，在设计冻结时集中登记。
同一删除完成后再次传入该 ID，若已不在 retained 且无待收尾记录，按未知目标处理；
操作恢复的幂等不等于任意未知 ID 删除都成功。

## 6. 删除与账本一致性：不能假设“失败即可回滚”

容器删除不可逆。本功能的恢复目标是**完成已确认操作的核验和账本收尾**，不是恢复已删数据。

建议阶段：

```text
PREPARED → REMOVE_REQUESTED → ABSENCE_CONFIRMED → LEDGER_UPDATED → FINALIZED
```

| 阶段 | 写入/动作 | 中断后的处理 |
| --- | --- | --- |
| PREPARED | 持久化已确认目标、完整归属、保护集合摘要、前态账本哈希和操作 ID | 重新核验；未确认删除发生前不擅自移除账本条目 |
| REMOVE_REQUESTED | 在调用 Docker 前写入操作意图，再发普通 rm | 结果可能已生效；必须 inspect 原完整 ID，不盲目重试或删同名容器 |
| ABSENCE_CONFIRMED | 目标在固定引擎上明确不存在 | 不再尝试恢复容器；幂等完成账本更新 |
| LEDGER_UPDATED | 原子移除目标条目，其他条目保持不变 | 核验后清除未完成标记 |
| FINALIZED | 输出实际完成结果 | 再次 recover 明确无操作需要恢复 |

要求：
- 若目标仍存在且所有删除资格仍成立，可在显式 recover 确认后重试普通 rm。
- 若目标变为运行中/受保护/身份异常，停止写操作并保留记录。
- 外部编辑了 retained 或角色记录，不能用旧快照覆盖；仅在能证明一致时更新指定条目。
- 删除成功而账本写入失败：输出“容器已删除，记录待收尾”，保留 journal，不返回完整成功。
- 写 journal 失败时不得发 Docker 删除；目标缺失与引擎离线必须走不同分支。
- 不把 remove 操作伪装为现有 switch/rollback；为 recover 明确区分操作类型和不可逆语义。

### 6.1 必须先解决的兼容性

当前旧版支持 state v2 和 env_version 1。仅增加一个旧程序不认识的文件，不能保证旧程序会阻断。
设计阶段须在“复用已识别未完成事务门禁”和“必要的 schema 升级”中选择可验证方案：

- 旧二进制不得忽略清理操作并同时 switch/rollback。
- 旧 recover 不得误将删除事务按切换事务解释。
- 新版须保持无删除操作的既有 v1/v2 项目可正常使用。
- 不要求仅查看 list 就升级用户本机状态。

冻结记录布局、版本策略和恢复方向后才能实现 remove；文档不能先宣称向后兼容。

## 7. 并发与资源保护不变量

- list 不产生变更；遇到正在变更的快照明确标记，不编造一致性。
- remove 与 switch/rollback/recover/init/stop/run 的变更路径复用项目级互斥。
- 正常 run/shell 已持锁时 remove 返回 BUSY，不强行与执行并发；list 仍可用。
- 未完成删除操作阻断其他变更；status/doctor/list 能说明待恢复内容。
- 当前项目保留记录的变化不影响其他项目；测试必须使用另一个项目的真实 ID验证拒绝。
- CURRENT、PREVIOUS、任何事务引用 ID，即便同时错误出现在 retained 中，也始终受保护。
- 正常操作成功后的资源集合仍满足：实际项目容器 = 当前代 + 上一代 + retained。
  中间态和 UNTRACKED 必须单独列出，不作为删除授权来源。

## 8. 分阶段任务包

### S0：基线与合同冻结
- 确认最新提交包含前序验收修复；保留已有未跟踪计划、备份和用户文档。
- 获得实施授权后再创建建议分支，不假设 master 已包含当前功能。
- 冻结角色/状态、完整 ID格式、错误码、普通 rm API、清理 journal 和旧二进制门禁。
- 将前序进度中陈旧的 NOT-RUN/未重跑表述同步为有证据的现状，不改写历史日志。

### S1：只读 list（独立交付点）
- 先写角色汇总、查询失败、重复/冲突记录、v1 兼容和无副作用测试。
- 批量枚举和逐项 inspect 使用固定 endpoint与完整 ID；不依赖显示短 ID。
- 接入帮助、status/doctor 相关提示；真实项目证明运行中任务不受影响。

### S2：remove 门禁与预览
- 先写反例：CURRENT/PREVIOUS/事务资源、真实跨项目 ID、running、未知状态均拒绝。
- 实现精确目标解析、只读预览、不可逆提醒、确认与取锁后重验。
- 为可删除、已缺失待清记录、拒绝三类结果提供不同输出。

### S3：普通删除、账本收尾与 recover
- 添加不带 force/volumes 的 runtime 删除入口及 argv 断言。
- 实现持久化意图、结果复核、目标条目原子更新、恢复幂等。
- 在所有写点、Docker 操作前后和响应丢失路径进行故障注入。

### S4：真实演练与安装版验收
- A→B→C 构造三个环境，list 显示 C 当前、B 回退目标、A retained。
- C/B 删除拒绝，A 预览无变更，确认后删除且记录同步。
- 验证 C 正常执行、仍能 rollback B，项目文件和其他项目未变。
- 补“删除已发生但记录未写入”的真实中断场景，并从安装版完成完整流程。
- 测试清理仅处理本轮完整 ID；保留资源和泄漏资源分开统计。

### S5：文档与独立审查
- 更新 CLI 合同、环境事务 ADR、用户指南、CHANGELOG、验证记录。
- 审查重点是误删保护、旧客户端门禁、不可逆操作恢复和测试实际覆盖。
- 输出分逻辑 diff 与提交建议；实际提交/推送仍待用户明确授权。

## 9. 验收矩阵

| 类别 | 必测反例/场景 | 证明内容 |
| --- | --- | --- |
| list | v1、只有当前代、多角色、空 retained | 无迁移写入，不虚构资源 |
| 查询分类 | 明确缺失、权限失败、超时、引擎离线 | MISSING 与 UNKNOWN 不混淆 |
| 身份 | 名称复用、短 ID、错误标签/挂载/镜像 | 不删除不符目标，完整 ID精确匹配 |
| 角色保护 | 当前代、回退槽位、事务资源、重复角色 | 保护优先，零 Docker 变更调用 |
| 并发 | 预览后 switch、取锁前角色变动、外部启动目标 | 不沿用旧确认、不强制删除 |
| 确认 | 拒绝确认、非交互无 --yes、dry-run | 零写入、零删除 |
| 删除成功 | 合法 exited retained | 普通 rm、确认不存在、仅删除指定条目 |
| 失效记录 | retained ID被外部删除，同名其他容器存在 | 只清理原 ID记录，不操作同名容器 |
| 响应丢失 | rm 已成功但客户端收到错误/断开 | 复核实态，不误报失败或重复删除其他资源 |
| I/O故障 | journal 写失败、删除后账本写失败 | 前者不删；后者报告部分完成且可恢复 |
| 中断 | 每个阶段 kill/fake 注入，再 recover | 可收尾，不宣称恢复已删除数据 |
| schema | 旧二进制遇到清理操作、损坏/未知 schema | 明确阻断，不按旧事务误恢复 |
| 跨项目 | 用 B 真实 retained ID从 A 删除 | 拒绝，B 容器与账本原样 |
| 不可逆边界 | 容器可写层金丝雀、项目文件金丝雀 | 前者随删除消失，后者保持；镜像/卷未被删除 |
| 正常回归 | list/remove 后 run/shell/rollback | 当前环境与回退能力不受影响 |
| 安装版 | dist→安装→list/remove/recover→卸载 | 不依赖开发二进制和源码目录 |

源码形态/argv 测试不能替代行为验证。真实强杀落点若没命中，应记为未命中并补测，
不能用流程已经成功退出冒充“删除后中断”证据。
