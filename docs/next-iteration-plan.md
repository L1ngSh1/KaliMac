# 下一阶段工程计划：候选版收口 → 一个只读扩展

状态：**待启动**。本文件只规划，v0.4.0-rc.1 本轮不实现新增功能。
原则：一次一个用户问题；先合同与反例，再最小补丁；每笔提交独立可构建、可回退。

## 1. 当前基线与目标

现有执行、会话恢复、环境切换/回退/清理功能已经形成完整操作链。
下一阶段先确保使用者能独立完成安装与首次上手，再做一个小扩展：
**为 `km tools` 增加 `--json`，让脚本读取工具可用性，不再解析面向人的表格。**

选择理由来自当前代码：`status` 已有 JSON，`tools` 只有文本，但二者都是只读查询。
本项复用既有工具清单与探测路径，避免引入安装器、后台服务或新的环境事务。
这是一项工程提案，不把尚未收集的用户反馈写成已确认需求。

## 2. S0：先收集候选版反馈

使用 v0.4.0-rc.1 的实际安装包，在独立项目记录：

- 安装路径/架构/Docker 状态、`km version --verbose` 与失败命令的完整退出状态。
- init → run → 共享文件 → shell → stop → 恢复是否无需开发者解释即可完成。
- sessions/cancel 与 env list 文案是否能指导下一步。
- Intel Mac 实机结果单独补齐；没有实机时继续标记待验证，不借用 Linux CI 结果。

产物：小型反馈表（问题、复现、影响、下一步），剔除凭空功能设想。
若出现数据、身份、事务或清理缺陷，优先单独修复并发布 rc.2；扩展项顺延。
退出门禁：无未解决的发布阻塞问题，安装版核心流程通过。

## 3. S1：冻结 tools JSON 合同（第一笔提交只做合同和测试）

建议分支：`codex/tools-json`，从当时最新已验证 master 开始。
实现前确认下列合同，保持文本默认输出与现有退出码不变：

```json
{
  "schema_version": 1,
  "container_state": "running",
  "tools": [{"name": "python3", "status": "AVAILABLE", "path": "/usr/bin/python3"}],
  "error": null
}
```

冻结要点：

1. stdout 恰好一个 JSON 对象，无日志混入；运行时错误用结构化 code/message，诊断不泄露环境秘密。
2. 正常查询返回固定六项、顺序稳定；MISSING 的 path 为 null；部分 MISSING 仍是成功查询（exit 0）。
3. Docker 不可达、协议异常、身份冲突、停止/暂停等状态不伪装成 MISSING；非零退出与文本口径一致。
4. 参数错误 exit 2，具体 JSON 错误是否覆盖解析失败在合同中明确后再实现。
5. 不启动容器、不写配置、不安装工具/会话脚本、不取执行锁；不增加 Docker 探测次数。
6. schema_version 与可选字段扩展规则固定，文案变化不影响机器字段。

先补负向测试：裸 126/127、缺行/重复行、空路径、含引号的诊断、停止/暂停、错误参数。
合同评审只解决上述边界，不扩展为通用 CLI JSON 重构。

## 4. S2：最小实现与验证

预计改动集中在 tools 命令、其测试、帮助与合同文档。优先复用现有 parseToolsOutput，
将采集结果与渲染分开；若引发多个管理命令重构，先拆出独立提案而不是顺手重做。

验收：

- 文本黄金样例不变；JSON 可解析且字段/顺序符合合同。
- fake 调用记录证明与原文本路径查询次数一致、写调用为零。
- before/after 配置与 .km 文件哈希一致。
- unit/race/vet/build 与真实 integration 全绿，零 SKIP、零残留。
- 安装版在 AVAILABLE、MISSING、停止和引擎查询失败四类场景按合同返回。

每次提交保留对应的反例、修复和验证记录；不以“总测试数增多”代替针对性证明。

## 5. S3：交付与回退

建议最多三笔逻辑提交：合同/测试、实现、文档/安装版证据。
PR CI 按实际 HEAD 核对。合并与发布各自记录 SHA；版本选择由变化和 rc 阶段决定，
不在本计划提前建立 v0.5.0 tag。

本项不改持久化状态格式，源码回退只需撤销相关提交；已发布安装包保持原样，修正发布新版本。

- 可复现工具镜像示例：先收集真实缺失工具需求，再选一个示例，不扩展为插件或包管理系统。

这些是候选后续项，不与 tools JSON 同一轮实施。
